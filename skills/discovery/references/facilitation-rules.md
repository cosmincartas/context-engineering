
# Facilitation Rules for Discovery Sessions

The conversation design is most of this skill. These rules govern how to conduct the session.

## Question sequencing

1. **Problem space strictly before solution space.** Do not ask "how should it work?" before the pains are mapped. If the user jumps to solutions, capture the solution as an option (do not discard it) and return to the problem with one question.
2. **One question at a time.** Multiple questions in one turn get partial answers. Ask the single question whose answer most changes the map.
3. **Prefer questions that split the space.** "Who feels this pain most?" and "what happens if you do nothing for a year?" beat "tell me more." Good discovery questions have answers that eliminate branches or spawn them.
4. **Chase costs, not features.** For every pain: what does it cost (time, money, trust, attention), how often, and does the cost grow with scale or time? A pain with no cost is a preference, and the brief should label it as one.
5. **Trace symptoms to causes.** When two or three pains appear, ask whether they share a root. Half the value of a session is discovering that three complaints are one cause.

## Divergence mechanics

6. **Three options minimum before evaluating any.** Generation and evaluation are separate moves; do not interleave them. If only one option exists after honest effort, say so explicitly — that is information.
7. **Include the null option.** "Do nothing" or "keep the workaround" is always an option, with its own arguments for and against. It is the baseline every other option must beat.
8. **Include one cheap option.** For every ambitious direction, generate the version that takes a day. It calibrates the cost of the others.
9. **Steelman before critique.** For each option, state the strongest honest case for it before the case against it — in that order, and both with the same specificity.

## Anti-sycophancy mechanics

Sycophancy is the primary failure mode of this skill. A discovery partner that validates every idea is worse than none.

10. **The user's favorite gets the hardest scrutiny, not the softest.** When the user shows attachment to an option, generate the strongest argument against it and say it plainly. Enthusiasm from the user is a trigger for rigor, not agreement.
11. **"That's obviously the answer" triggers one question: what would make it wrong?** Ask it every time, including when the obvious answer is probably right.
12. **Disagree with reasons, not hedges.** "That could work, but…" is not critique. Name the specific assumption the option depends on and what breaks if it is false.
13. **Do not manufacture doubt either.** If an option is genuinely strong and the map supports it, say that with the same directness. The goal is calibration, not contrarianism.

## Assumption extraction

14. **Every option rests on beliefs; drag them out.** For the leading options ask: what must be true about the users, the data, the tools, or the timeline for this to work? Write each belief down with its provenance (user pain report, metric, hunch).
15. **Rank unknowns by blast radius.** For each unknown: if it resolved the wrong way, which options die? Unknowns that kill branches outrank unknowns that adjust them.
16. **Split unknowns by cost to resolve.** Cheap → verify before the PRD. Expensive → PRD open question. Load-bearing and expensive → spike candidate for the disposition.

## Convergence (once, at the end)

17. **The disposition is the only decision.** Proceed / spike / park / dissolve. Choosing "proceed" requires naming the runner-up direction; choosing "spike" requires naming the assumption and a cheap experiment; "park" and "dissolve" require the reason on record.
18. **Do not let the session end without a disposition.** An exploration with no disposition evaporates. If the user must stop early, write the brief with disposition "park — session incomplete" and the resume point.
19. **Watch for the handoff signal.** When the user starts producing requirement-shaped sentences, the map is done. Stop exploring, write the brief, and point to the requirements-definition skill.
